# Deploying to Render

This deploys `apps/api` (GraphQL + REST — everything your custom application would call) as a
Render web service. MCP is **not** covered here — it currently only runs over stdio (spawned as
a local process), not as a hosted HTTP service; see `docs/BUILD_STATUS.md` if/when that changes.

## Prerequisites

- This repo pushed to GitHub (already done — `main` branch).
- A reachable Postgres database. This repo's own dev/test environment uses a managed **Neon**
  instance — either reuse that connection string or provision your own Postgres (Render's own
  managed Postgres works too, or any other host).
- A reachable Redis instance (Redis Cloud, Upstash, Render's own managed Redis/Key Value, etc.).
- A [Render](https://render.com) account.

## 1. Deploy via Blueprint

The repo includes `render.yaml` at the root, which Render can use to provision the service
automatically:

1. In the Render dashboard: **New → Blueprint**.
2. Connect this GitHub repo, branch `main`.
3. Render reads `render.yaml` and shows one service to create: `leanix-mock-api`.
4. Before/after creating it, fill in the secrets it left blank (`sync: false` in the blueprint
   means Render won't guess a value — you set it):
   - `DATABASE_URL` — your Postgres connection string (e.g. the Neon one, including `&pgbouncer=true`
     if it's a PgBouncer-pooled endpoint — see `docs/BUILD_STATUS.md` for why that matters)
   - `REDIS_URL` — your Redis connection string
   - `LEANIX_API_TOKEN` / `LEANIX_API_TOKEN_SECRET` — pick your own credential (or reuse the
     repo's defaults, `dev-token-12345` / `dev-secret-67890`). These are only *read at seed time*
     (step 2 below) to register the technical user's actual credential in the database — the
     token endpoint validates against that exact stored value, not a pattern, so whatever you
     put here is what your custom application must send.
   - `JWT_SECRET` is auto-generated by the blueprint (`generateValue: true`) — no action needed.
5. Click **Apply**. Render will:
   - `npm install`
   - build `packages/shared`
   - generate the Prisma client
   - run `prisma migrate deploy` against your `DATABASE_URL` (creates the schema — safe to
     re-run on every deploy, it's idempotent)
   - build `apps/api`
   - start it with `node apps/api/dist/main.js`

Deploys are gated on `GET /health` returning 200 before Render routes traffic to the new
instance.

## 2. Seed the database (first deploy only)

`render.yaml`'s build step does **not** run the seed script (it would re-seed on every deploy,
which is wasteful and not usually what you want after the first time). Run it once, pointed at
the same `DATABASE_URL`/`LEANIX_API_TOKEN`/`LEANIX_API_TOKEN_SECRET` you gave Render — the seed
is what actually **registers** that technical-user credential in the database; the token
endpoint won't accept it until this runs:

```bash
DATABASE_URL="<same value you put in Render>" \
LEANIX_API_TOKEN="<same value you put in Render>" \
LEANIX_API_TOKEN_SECRET="<same value you put in Render>" \
npm run prisma:seed
```

Run this from your own machine (or Render's **Shell** tab on the service, once it's live).
Re-running it later with different `LEANIX_API_TOKEN`/`_SECRET` values rotates the credential.

## 3. Verify

```bash
BASE_URL="https://<your-service>.onrender.com"

curl "$BASE_URL/health"

curl -X POST "$BASE_URL/services/mtm/v1/oauth2/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data "grant_type=client_credentials&client_id=dev-token-12345&client_secret=dev-secret-67890"
```

Then open in a browser:
- `https://<your-service>.onrender.com/api-docs` — Swagger UI (REST)
- `https://<your-service>.onrender.com/services/pathfinder/v1/graphql` — GraphQL Playground

## 4. Point your custom application at it

Whatever config your application uses for `LEANIX_BASE_URL` (see `docs/MIGRATION_GUIDE.md`),
set it to the Render URL instead of `http://localhost:4000`. Everything else (paths, auth flow,
GraphQL schema, error codes) is unchanged — that's the whole point of the adapter pattern.

If your application runs in a browser and calls this API cross-origin, either leave
`CORS_ORIGIN=*` (fine for testing) or set it to your app's real origin(s) — comma-separated if
more than one — once you know them, so the API isn't wide open to any origin in a shared/public
deployment.

## Known limits on Render's free tier

- **Cold starts**: free web services spin down after ~15 minutes of inactivity and take a
  noticeable few seconds to wake back up on the next request. If your custom application needs
  consistently fast responses, use a paid plan (or a periodic health-check ping to keep it warm).
- **No local disk persistence** — irrelevant here since all state lives in Postgres/Redis, not
  the filesystem.
- Combined with a remote Postgres/Redis (see `docs/BUILD_STATUS.md`'s latency notes), expect
  meaningfully higher per-request latency than running this locally against local services —
  that's real network round-trip time, not a bug.
